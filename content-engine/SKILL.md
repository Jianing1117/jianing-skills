# 内容引擎

```
   别人的爆款 ──【学】──→ 拆解卡 ──→ 审阅 ──→ 方法论
                                              │
                                              │ 读
                                              ▼
   我的内容 ────【改】── 先诊断 ──→ 定位部位 ──→ 标题 / 开头 / 正文 / 切片
                                              │
                                              ▼
                                      发布 → 数据 ──【复盘】──┐
                                              ▲                │
                                              └────────────────┘
```

**方法论是轴。学写它，改读它，复盘校准它。** 引擎本身只是工序，判断依据一律去读文件——说不出依据的判断，是你在编，删掉。

## 写入纪律（红线）

1. **默认只在对话里输出，不落盘。**
2. **审阅门**：任何要落盘的内容，先在对话里出完整一版，逐条点头 / 否掉 / 改。**没有明确点头就不写。**
3. 获准后只写这三个地方：

   | 写什么 | 写去哪 |
   |---|---|
   | 提炼出的通用规律 ＋ 内嵌证据行 | 本 Skill `playbook.md` 对应小节 + 更新日志一行 |
   | 自家数据得出的结论 | vault `方法库/爆款心得与标题公式.md` + 该文件更新日志 |
   | 可迁移性判定结果（✅ / ⚠️ / ❌） | vault `方法库/适合我的爆款条件.md` 对应小节 |

   **拆解卡不落盘。** 它是给用户审阅用的中间产物，看完即弃——要留下的东西已经压缩进 playbook 条目的证据行里。**vault 结构零改动，不新增任何文件或文件夹。**

4. **宪法层（`系统规则/`）永不由本引擎修改。** 只能提议，留到月度复盘由用户决定。
5. 写 vault 前先打 checkpoint：`git -C "<vault>" add -A && git -C "<vault>" commit -m "checkpoint: content-engine 沉淀前"`
6. **脱敏铁则**：进 `playbook.md` 的内容不得包含真实经营数字、客户信息、未公开的个人经历。绝对数字改成量级或比率区间。

# 一、【学】拆爆款

输入：视频链接 / 转写 / 截图 / 点点的分析 / 用户自己的批注。有几样用几样，缺的就问，不猜。

### 流程

1. 读主控（形/神怎么分、什么是一票否决）＋ 现有 `playbook.md`（避免重复沉淀已有规律）
2. 按 0–6 层出**拆解卡**（格式见下），每层带引文或评论作证据
3. §5 做**可迁移性三档**，§6 给**对本账号的启发**（版面 · 谁能产 · 具体选题）
4. **交给用户审阅** —— 逐条点头 / 否掉 / 改
5. 通过的部分：提炼成规律写进 `playbook.md`，并把这条爆款压成一行证据挂在下面。**卡片本身不落盘。**
6. 可迁移性判定的结果落进 vault `方法库/适合我的爆款条件.md`——✅ 和 ⚠️ 进正文，❌ 进反面清单。**这是唯一记录「什么适合我」的地方，不落就白判了。**

### 拆解格式（0–6 层，每层带证据）

输入三样：**爆款全文**（口播稿/图文）· **账号信息与数据**（粉丝、赞藏评）· **评论区高赞前 10 条**。评论区拿不到就照常拆，但 §4 留空并在开头标「未经观众证词校验」。

```markdown
# [一句话：观众完成了一次什么体验]
（不是"它讲了什么"，是"观众经历了什么"）
链接 · 平台 · 时长 · 粉 X 赞 X 藏 X 评 X · 赞粉比 X 倍

## 1 底层判断
它押中的反常识判断是什么？一句话 + 原文引文。
没有反常识判断 → 明说它赢在别处（时机 / 情绪 / 颜值 / 流量），不硬找。

## 2 结构
开头让观众以为会得到什么 → 中间实际给了什么 → 结尾把观众带到了哪里。
**自证结构**：它讲的技巧，这条内容自己有没有在用？有 → 指出具体怎么用的；没有 → 如实写「无自证结构」。

## 3 人格层
哪一句、哪一段暴露了真人（真实经历 / 矛盾 / 恐惧 / 付出的代价）？创作者有没有把创作意图摊开讲？
全程无人格暴露 → 明说「纯干货型爆款」。

## 4 观众证词
评论区高赞里，观众自己说出的被打动的理由，**直接引用原句**。
这是检验前三层的唯一硬证据——分析和评论对不上时，以评论为准，回头修正前三层。

## 5 可迁移拆分
✅ 可复制（结构 / 公式 / 句式）→ 每条写成一条可直接执行的操作规则
⚠️ 需翻译 → 机制对，但原话本账号说不出口。**当场写出本账号的版本**，写不出就降成 ❌
❌ 不可搬（人格 / 经历 / 账号积累）→ 明确标注，说清为什么

## 6 对本账号的启发（最多两条，每条三项必齐）
① 对应哪个版面（读宪法层的版面定义）
② 谁能产：团队可写 / 需要用户一段语音判断 / 只能用户本人
③ 一个具体选题，或一条具体改法
```

### 拆解纪律

- **每个判断必须附原文引文或评论作证据。** 没证据的判断，删掉。
- **§6 只能基于宪法层里的账号背景**（记忆点 · 人设 · 受众 · 对立面 · 铁则），不得假设账号在做其他方向的内容。
- **禁止没有动作的建议**——「要真诚」「要做自己」这类一律不写。
- 拿不准就写「拿不准」，不要编。
- **全文不超过 1000 字。** 写长了说明没抓住爆点。
- **形可以抄，神要问资格。** 主控 §2：「语气是形，可模仿；立场和经历是神，模仿不了。」§5 里一条做法如果需要用户没有的经历或身份才成立，判 ❌。
- **低粉高赞单独看**：粉丝少还爆，爆点几乎全在内容本身。这类样本 playbook 单开一节收。

### 落盘（用户点头后）

| 拆解卡里的 | 去哪 |
|---|---|
| §5 的 ✅ 和 ⚠️ 提炼成通用规律 | 本 Skill `playbook.md`，挂一行证据 |
| §5 三档判定 + §6 启发 | vault `方法库/适合我的爆款条件.md` 对应小节 |
| 拆解卡本身 | **不落盘**，看完即弃 |

### 进 playbook 的方式

卡片不留，所以**规律必须当场进 playbook**，否则下次就想不起来了。进的时候带一行证据：

```
- [链接] · 粉X 赞X · 赞粉比 X 倍 · [一句话：它在这条规律上具体做了什么]
```

| 置信度 | 条件 | 诊断时能不能当依据 |
|---|---|---|
| **参考** | 1 条证据 | 收进来并标注，**只作参考，不作依据** |
| **已印证** | ≥2 条**独立**证据 | 可以当依据引用 |
| **自家验证** | 自己发内容验证过 | 优先使用 |

被数据推翻的条目**不删也不降级**——在条目下加一行 `❌ 已推翻（日期·原因）`，正文划掉。反面教材和正面规律一样值钱。

第二条爆款指向同一条规律时，**不新开条目**——找到已有条目追加一行证据，升级置信度。

与 playbook 已有条目**冲突** → 不覆盖，并列写出来，两条都标"待验证"，等数据裁决。

# 二、【改】诊断并优化

**诊断先行。** 用户说"改开头""优化标题"，都先走一遍诊断——很多时候问题不在他说的那个部位。

### 第一步：诊断（永远先跑，不跳过）

按顺序，前面不过就别往后做：

**1. 主控四问**（读主控 §9，用用户自己的四问，不是通用四问）

四问不过是**选题层面的问题，改文案救不了**。直接告诉用户："这条的问题不在文案，在第 2 问没过。要么换角度重写，要么换选题。"

**2. 一票否决扫描**

逐条扫主控 §2「永不说、永不做」＋ 平台合规红线（诱导互动等，见 `awesome-creator.md`）。命中即必改，不商量。

**3. 全片四维**（不只看前 3 秒）

| 维度 | 看什么 | 判定 |
|---|---|---|
| **结构** | 属于哪种内容原型？骨架完整吗？缺哪一环？ | |
| **节奏** | 每 15–30 秒有没有继续看的理由？哪里有平段？ | |
| **信息密度** | 单位时间的新信息量。哪里注水、哪里过密到跟不上？ | |
| **收尾** | 有没有落回核心记忆点？带 slogan 了吗？**离场感是更安心还是更焦虑？** | |

**4. 完成度阶梯**（主控 §2）

60% = 只有语气 ｜ 80% = 语气 + 可截图的判断 ｜ 100% = 语气 + 判断 + 真实经历

判出档位，并说清**差什么才能上一档**。

### 诊断与手艺的分工（别让两边都写规则）

| | 负责 | 不负责 |
|---|---|---|
| **诊断（本文件）** | **判**——哪个部位有问题、多严重、定位到 `awesome-creator.md` 的哪一节 | 不给具体做法 |
| **`awesome-creator.md`** | **改**——每个部位的具体做法、模式、句式 | 不判好坏 |

同一个话题会在两边出现（"互动钩子"既是诊断维度也是手艺），**但方向相反**：诊断问「这里缺不缺钩子」，手艺库答「钩子怎么写」。**规则只写一遍，写在手艺库；诊断只引用，不复述。** 发现两边在写同一条规则，删掉诊断这边的。

### 第二步：定位部位，调用手艺

诊断出问题在哪，再去 `awesome-creator.md` 取对应方法：标题 / 开头 / 正文结构 / 互动钩子 / 切片。

同时读 `playbook.md`——有相关规律就用，并**注明依据哪一条**。

### 第三步：出修改建议

分两级，**每条都要给可直接替换的文本，不许只说"这里不够好"**：

```
🔴 必改：[问题] → [替换文本]     依据：[主控§X / playbook§X / 适合我的爆款条件§X]
🟡 建议：[问题] → [替换文本]     依据：...
```

只有两级。想不清楚该放哪一级的，就是 🟡。**凑不出理由的第三级"可选"，本质是噪音。**

逐段诊断格式：

```
### 第 N 段 ·「[原文首句…]」
诊断：
依据：
改法：[可直接替换的文本]
```

### 切片（长内容 → 短内容）

一支中长视频切出 3–5 条能独立成立的判断，每条写成 60 秒口播。

**判断 ≠ 步骤**——这是切片唯一的难点，也是最容易做砸的地方。筛选标准、60 秒骨架、输出要求见 `awesome-creator.md` §5。

# 三、【复盘】月度数据回流

### 节拍：月度，不是周度

小红书内容靠搜索长尾持续吃流量，一条笔记 7 天的数字不是终值；而且一周只有三五条，率是噪音。所以**只在月度读数据**。

| 节拍 | 谁 | 做什么 |
|---|---|---|
| **随时** | 用户 | 看到哪条起量 / 扑了 / 低粉高赞，跟引擎说一句 → 引擎当场按【学】拆一次，证据标「自家验证」。不导出、不读文件 |
| **月度** | 用户 | 从创作者中心导一次 xlsx，扔进 `复盘分析/数据/`（文件名带日期即可） |
| **月度** | 引擎 | 读本月 + 历史数据 → 台账 + 复盘初稿 → **回看方法论** → 出提议清单 |

### 月度复盘的「回看方法论」

台账和复盘初稿之后，多跑一道：

- `playbook.md` 里哪条被本月数据**验证**了 → 升置信度
- 哪条被**推翻**了 → 加 `❌ 已推翻` 标记，不删
- 哪条「参考」级的够格升「已印证」
- `方法库/爆款心得与标题公式.md` 要不要追加自家数据得出的新结论

全部**先出清单，用户点头，才动文件**。宪法层永远只提议。

### GitHub 发版

**周节拍收口**：每周看一次 `playbook.md` 有没有变化，有就发版，没有就跳过。不攒着，也不硬凑。

playbook 的主要增长来源是拆解，不受样本量限制——一条爆款就是一条真实证据，所以周周有东西可发是正常的。只有自家数据的结论要等月度。

发版前：

1. 脱敏检查：真实经营数字、客户信息、未公开经历，一律不进
2. 更新 `playbook.md` 顶部版本号与文末更新日志
3. commit message 写清这版学到了什么——git log 本身就是方法论进化史
4. **推送前给用户过一遍**，点头才 push

## 分工：谁分析，谁落盘

| | 谁 | 说明 |
|---|---|---|
| **分析** | 任何 AI | 点点（懂平台侧）、Hermes、Cowork、Codex——多个角度反而好。用户把结论带回来 |
| **评估** | 本引擎 | 外部结论一律过可迁移性判定，**平台上有效 ≠ 这个账号能用**。冲突时并列写出、标清来源，交用户裁决 |
| **落盘 + 版本管理** | **只有本引擎** | 写 `playbook.md`、写 vault、git 提交与发版。**单点写入，避免两个 agent 改同一个文件冲突** |

外部 AI 的分析进 playbook 时，证据行注明来源（如「点点」），和引擎自己拆的区分开。
